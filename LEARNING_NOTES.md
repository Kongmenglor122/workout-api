## Backend Learning Notes

### Project Setup
- Use a virtual environment to isolate project dependencies.
- Install dependencies with `python -m pip install -r requirements.txt`.
- Record installed versions with `python -m pip freeze > requirements.txt`.
- Run the API with `python -m uvicorn app.main:app --reload`.
- Open `/docs` to explore and test endpoints.

### Git and Local Configuration
- Git commits save local snapshots; pushing uploads commits to GitHub.
- `.gitignore` excludes local files such as `.venv/`, `.env`, and `.vscode/`.
- `.env` holds actual local configuration and credentials.
- `.env.example` documents required settings using placeholders.
- Never commit real credentials.

### PostgreSQL
- PostgreSQL is the database server; psql and pgAdmin are clients.
- Installing a client does not confirm that a server is running.
- Check the server address, port, username, and database when connecting.
- SQL commands run inside psql; Python and Git commands run in the terminal.
- Keep pgAdmin compatible with the PostgreSQL server version.

### Application Structure
- `main.py` creates the application and registers routers.
- `config.py` loads settings, including values from `.env`.
- `database.py` configures the engine, sessions, and shared model base.
- `models.py` describes database tables.
- `schemas.py` validates API requests and defines responses.
- Routers handle HTTP requests and coordinate database operations.
- Filenames are conventions; importing the correct module matters.
- Database-backed features often start with models and schemas, but not every endpoint needs a model.

### SQLAlchemy Models
- Models inherit from our shared `Base`.
- `Base` inherits SQLAlchemy functionality from `DeclarativeBase`.
- `pass` leaves the class body empty without removing inherited behavior.
- `__tablename__` sets the database table name.
- `Mapped[...]` describes an attribute managed by SQLAlchemy and its Python type.
- `mapped_column()` configures the database column.
- A primary key uniquely identifies a record.
- Our integer primary keys are generated by PostgreSQL.
- Allowing `None` in a mapped type normally makes the column nullable.
- Required timestamps do not automatically receive the current time unless a default is configured.
- Import models before calling `Base.metadata.create_all(bind=engine)`.
- `create_all()` creates missing tables; migrations manage later structural changes.

### Database Sessions
- The engine manages database connections.
- `SessionLocal` creates sessions.
- Sessions query records and track changes.
- `Depends(get_db)` provides a session to an endpoint.
- `yield` lets the endpoint use the session before cleanup.
- Closing a session does not commit changes.

### Pydantic Schemas
- Schemas inherit from `BaseModel`.
- Request schemas describe accepted input.
- Response schemas describe returned output.
- Use separate schemas for creation, updates, and responses.
- Creation requests omit database-generated IDs; responses can include them.
- `str | None` allows null but does not make a Pydantic field omittable.
- Adding `= None` allows the field to be omitted.
- `from_attributes=True` lets Pydantic read SQLAlchemy object attributes.
- Database column constraints and API validation are separate concerns.

### FastAPI Requests and Responses
- Routers group endpoints using prefixes and documentation tags.
- Register routers with `app.include_router(...)`.
- Path placeholder names must match function argument names.
- Typed path arguments are converted and validated by FastAPI.
- Invalid request input automatically produces a 422 response.
- Swagger UI may block invalid input before sending a request.
- Raise `HTTPException` for cases such as a missing record.
- A Pydantic model argument is normally read from the JSON request body.
- Use `:` for type annotations and `=` for default values.
- Put `response_model` in the decorator, not the function arguments.
- Returning a SQLAlchemy object gives it back to FastAPI, which validates and serializes it using the response model.
- Use a list response model when returning multiple records.
- JSON field order does not affect meaning.
- Documentation summaries default to readable versions of function names and can be customized.

### CRUD Operations
- Create: build an object, call `add()`, `commit()`, and `refresh()`.
- Read one: use `db.get(Model, primary_key)`.
- Read many: use `select()`, `db.scalars()`, and `.all()`.
- Use `order_by()` when a predictable result order is required.
- Update: retrieve an object, change its attributes, commit, and refresh.
- Retrieved objects are already tracked by the session.
- For PATCH, `model_dump(exclude_unset=True)` keeps only explicitly submitted fields.
- Omitted PATCH fields stay unchanged; explicit null values need validation against database rules.
- `setattr(object, field, value)` updates an attribute dynamically.
- Delete: retrieve the object, call `db.delete(object)`, then commit.
- `db.delete()` takes an object, not a model class and ID.

### HTTP Status Codes
- 200: successful request with a response.
- 201: a record was created.
- 204: success with no response body.
- 404: the requested record was not found.
- 422: request validation failed.

### Learning Approach
- Build and understand synchronous CRUD before introducing async.
- Practice writing features independently, then review and test them.
- Test successful requests, missing records, and invalid input.
- Learn migrations, relationships, authentication, testing, async, and deployment as the app grows.
